### Task 1: D3, a guard over every shader patch

**Files:**
- Create: `test/shaderpatches.test.js`
- (Optional) Create: `test/helpers/shaderpatch.js` if the capture helper is worth sharing; otherwise keep it in the test file.
- No `src/` edits.

**Why:** the game patches three.js shaders in about 38 places (`material.onBeforeCompile = (shader) => { shader.fragmentShader = shader.fragmentShader.replace('#include <x>', ...) }`, across `src/render/`, `src/world/`, `src/cat/`, `src/weather.js`, `src/race.js`, `src/treefade.js`). If a three.js upgrade renames a chunk, `String#replace` finds nothing and the patch silently does nothing. This test must fail instead.

**Approach (behavioural, no source reading):**
1. In the test, before importing game modules, replace `THREE.Material.prototype.onBeforeCompile` with an accessor property (get/set) so every assignment `m.onBeforeCompile = fn` anywhere in the game is captured as `{ material, fn, site }`, where `site` is the first stack frame outside the test and outside `node_modules` at assignment time (`new Error().stack`, file + line). The getter must still return the assigned function so the game's own chaining (`const prev = material.onBeforeCompile`, clones copying it) keeps working; the default (never assigned) returns three's no-op method.
2. Exercise every patch site the game has: build every area builder (`neighborhood, park, seaside, docks, woods, river, moor, pines, gorge, den, farm, fair`, the same `BUILDS` table test/clouds.test.js uses) into a scene, and create the per-walk systems that patch materials (grass, water, water dressing, clouds, splash, paw prints, ambient, dusk lawn, rustle, weather/rain, race pads, tree fade, the cat with its rim light and face lens glow). Reuse the canvas stub from `test/helpers/growriver.js` (`canvasStub`) for `document`. Look at how existing tests construct each system (e.g. test/clouds.test.js, test/catrim.test.js, test/fairlights.test.js, test/builder.test.js) and copy their construction calls, not their text pins.
3. For every captured patch, build the shader object three would pass: pick the ShaderLib entry for the material's type (`MeshStandardMaterial → ShaderLib.standard`, `MeshPhysicalMaterial → physical`, `MeshLambertMaterial → lambert`, `MeshBasicMaterial → basic`, `MeshPhongMaterial → phong`, `MeshToonMaterial → toon`, `MeshMatcapMaterial → matcap`, `PointsMaterial → points`, `SpriteMaterial → sprite`, `ShadowMaterial → shadow`, `MeshDepthMaterial → depth`, `MeshDistanceMaterial → distance`, `LineBasicMaterial → basic`), with `vertexShader`, `fragmentShader`, `uniforms: THREE.UniformsUtils.clone(lib.uniforms)`, `defines: {}`. A type with no entry is a test failure that names the site.
4. Call the captured `fn(shader, fakeRenderer)` while `String.prototype.replace` and `String.prototype.replaceAll` are wrapped: any call whose receiver is a shader-sized string (contains `void main`) and whose result equals its input is recorded as a no-op. Restore the prototypes in `finally`.
5. Assertions:
   - `it.each` over captured sites (deduplicated by `site`): no replace was a no-op, and at least one of `vertexShader` / `fragmentShader` changed. A failure message names the site and the search value that matched nothing.
   - A sanity test that proves the guard works: a material whose patch replaces `'#include <no_such_chunk>'` is reported as a no-op.
   - A coverage floor: the number of distinct patch sites captured is at least the number found when the test is written (record it in a named constant with a comment saying: raise it when a patch is added; a drop means a patch is no longer exercised here). Find today's number by running the test.
6. Keep the test under ~60 s on this Mac; if building every area is slow, build each once in `beforeAll`. If it is a heavy file (over ~20 s), add it to the heavy list in `test/heavy.js` following that file's pattern.

- [ ] Add the per-site checks and coverage floor; run; every real site passes (if one genuinely no-ops today, that is a bug the test found: report it, do not fix game shaders in this task).
- [ ] Full suite once, then commit `test/shaderpatches.test.js` (and the helper / `test/heavy.js` if touched): `D3: one test guards every shader patch against a renamed three.js chunk`.

**D4a, `navigator.storage.persist()` once, guarded and quiet.** `src/savekeep.js` exports `askToKeepSaves(nav = globalThis.navigator)` returning a Promise that never rejects and resolves to `true`, `false`, or `null` (not asked). Rules:
- At most once per page load (a module-level flag; a second call returns the first call's promise).
- No `nav`, no `nav.storage`, or `persist` not a function → `null`, nothing called.
- If `nav.storage.persisted` is a function and resolves `true` → `true`, `persist` not called.
- Quiet: if `nav.permissions?.query` exists and `query({ name: 'persistent-storage' })` resolves to `'prompt'` or `'denied'`, do not call `persist()` (Firefox shows a permission prompt for it; Chrome answers silently from its own heuristics either way). If the query throws or rejects (Safari does not know that permission name), call `persist()`.
- Any throw or rejection anywhere → resolves `null`, with no console output and no diagnostics note (this is optional hardening, not a failure).
- main.js calls it once at boot, fire-and-forget, after the progression is created, in every build (the iOS app included: it is harmless where unsupported).
- Tests in `test/savekeep.test.js` with fake navigators: absent API; already persisted; query says prompt (persist not called); query throws (persist called); persist rejects (resolves null, no throw); called twice (persist called once). Use `vi.resetModules()` + dynamic import per test for the once-flag.

It bumps `version` (so the readout redraws) but not `total`. `clear()` empties it too. Wrapped like `note`: it can never throw. Export a module-level `noteMemory(info)` beside `note`.
