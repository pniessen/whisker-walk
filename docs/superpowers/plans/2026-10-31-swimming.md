# Swimming and Wading Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every cat can wade into a shallow band at the shore; Sea Legs lets it swim the deep water. Wading looks like sketch C, swimming like sketch A, and climbing out ends with sketch D's shake. No map gains a crossing for a cat without Sea Legs.

**Architecture:**
- **Depth.** `world/builder.js` gains a "real shore": every footprint edge, minus the parts that run under another water. The depth used for shallow and deep is the distance to that shore. Each footprint declares its own `shallow` width.
- **Movement.** A pure water state machine (`src/waterstate.js`) decides dry, wade or swim, with hysteresis. It also times the shake. The player owns one copy. Each remote co-walk cat gets its own, computed from its drawn position.
- **Look.** The look is three new animator states (`wade`, `swim`, `shake`). The cat group also sinks: the water surface is opaque, so anything below the waterline is hidden for free.
- **Effects.** Splashes, ripples and droplets are one pooled module, `render/splash.js`, with two instanced draws.

**Tech Stack:** Three.js 0.185, Vite 8, Vitest 4. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-31-swimming-design.md`. Read all of it before Task 1.

## Global Constraints

- `SAVE_VERSION` stays 4. Nothing new is stored, and nothing goes on the wire: `sendState`'s `pose` keeps today's meaning (the land pose).
- Only the player is pushed by water. Critters, strays, ghosts, the kitten and toys keep ignoring it. Remote co-walk cats only *look* wet.
- Decks (pier, bridges, stepping stones, the log) stay dry ground. Wading never starts on a deck.
- No new bank-to-bank route for a cat without Sea Legs. `test/wadingroutes.test.js` (Task 2) is the proof.
- No jitter at the shallow/deep line, or at the waterline.
- Effects are pooled: no per-frame allocation, at most 2 extra draw calls, and 0 when no cat is in water.
- Reduced motion:

## Defaults this plan picks (the spec leaves them to the builder)

| What | Value | Why |
|---|---|---|

| `shallow`, River `pool-1..3` | 1.0 m | Small pools (r 2.5–3.5) keep a swimmable middle. |
| `shallow`, every other water | 1.2 m | Every 5 m river keeps a deep middle of 2.6 m. Worst same-bank saving measured: 5.6 m. |
| Wading speed `WADE_SPEED` | 0.8 of pace | From the spec. 0.8 × the dry pace is under the zoomies' 0.85 line, so zoomies can't charge in the shallows. |
| Swimming speed | `SWIM_SPEED` 0.55, unchanged | |

### Task 1: The real shore, and depth measured to it

**Files:**

**Interfaces:**
- Produces, from `src/world/builder.js`:
  - A footprint may carry `shallow: number`, in metres; missing means 0. `waterGap`, `waterClearance`, `inWater` and `nearestDry` ignore it.
  - `shorePieces(waters) -> ReadonlyArray<{ ax, az, bx, bz, shallow, id }>`
    - The real shore as segments, cached per `waters` array in a module `WeakMap`.
    - A rect gives its 4 edges. A circle gives `CIRCLE_CHORDS = 64` chords.
    - A piece is dropped where it lies strictly inside another footprint (`waterGap(o, x, z) < −1e-6`, `o !== w`).
    - Pieces are never clipped by decks: water under a deck is still deep.
  - `shallowExcess(waters, x, z) -> number`
    - Returns `−Infinity` when `waterClearance(waters, x, z) >= 0`, which covers dry ground and decks.
    - Otherwise returns `min over pieces p of (distance from (x, z) to p) − p.shallow`.
    - ≤ 0 is the shallow band; > 0 is deep.
  - `nearestShallow(waters, x, z, margin, out) -> out`
    - Fills `out` (`{ x, z }`) with the nearer of two candidates:
      - the band point on the piece that sets `shallowExcess`: the point at distance `p.shallow` from its nearest point q, on the ray from q through (x, z);
      - `clampInto(d, x, z, margin)` for each deck of each footprint containing (x, z).
    - No allocation except `clampInto`'s return value.

  - `createWaterState() -> { mode: 'dry', wetTime: 0, swam: false, shake: 0, entered: false, shook: false, sink: 0, fxClock: 0, ringClock: 0 }`
  - `stepWaterState(st, waters, x, z, dt) -> st` mutates `st`. Each step clears `entered` and `shook` first, then follows these rules:
    - **Dry, and `waterClearance < 0`:**
      - set `entered = true`, `wetTime = 0`, `swam = false` and `shake = 0`;
      - the mode is `'swim'` if `shallowExcess > DEEP_HYST`, else `'wade'`.
    - **Wet, and `waterClearance > DRY_HYST`** (Infinity on a deck counts):
      - the mode becomes `'dry'`;
      - if `(swam && wetTime >= SHAKE_AFTER_SWIM) || wetTime >= SHAKE_AFTER_WADE`, then `shake = SHAKE_TIME` and `shook = true`.
    - **Wet otherwise:**
      - `wetTime += dt`;
      - `'wade'` becomes `'swim'` when excess > `DEEP_HYST`;
      - `'swim'` becomes `'wade'` when excess < −`DEEP_HYST`;
      - set `swam = true` while swimming.
    - **Empty `waters` or `null`:** treated as dry ground. This is the perched and no-water path, and the leaving rule above still runs.
    - **Always:** `shake = max(0, shake − dt)`.
  - `shakeProgress(st) -> number` is `1 − st.shake / SHAKE_TIME` while shaking, else 0.
- Produces, from `src/player.js`:
  - Plain api fields written by `update`:
    - `water`: `'dry' | 'wade' | 'swim'`;
    - `swimming`, which now means deep water only;
    - `wading`;
    - `inWater`, which is wading or swimming;
    - `shaking`, which is `shake > 0`;
    - `waterState`, the player's state object (the same object every frame).
  - `setAvatar` resets the state with `Object.assign(st, createWaterState())`.

  - **`'wade'`:**
    - the walk gait at 0.7 × the walk frequency;
    - amplitude `min(0.75, 1.5 × the walk amp)`;

  - `splashEmits(st, speed, dt, reducedMotion, out) -> out`. It is pure: it advances `st.fxClock` and `st.ringClock` and fills `out = { drops, wake, ring, puff }` with counts:
    - wading with speed > 0.3: `drops` 3 every 0.22 s;
    - swimming with speed > 0.3: `wake` 1 (a left-and-right pair) every 0.16 s, and `ring` 1 every 0.6 s;

  - `createSplash(scene, { tier, reducedMotion }) -> { meshes, capacity, track, update, dispose, get drawCount }`.
    - **Drops:** an `InstancedMesh` of `IcosahedronGeometry(0.025, 0)`, `MeshBasicMaterial` 0xdff3ff with opacity 0.85. Each drop is a ballistic arc under 9.8 gravity, with a ttl of 0.45 s (0.6 s for the puff, 0.3 s under reduced motion).
    - **Rings:** an `InstancedMesh` of a flat `RingGeometry(0.85, 1, 24)` at y `WATERLINE + 0.005`, `depthWrite: false`. Each instance has an `aAlpha` attribute, patched in the way `render/pawprints.js` does it. A ring grows 0.15 → 0.6 m over 1.2 s, or 0.2 → 0.9 m over 1.6 s when still, and fades out.
      - Wake rings start ±0.18 × scale to the side and 0.35 × scale behind, and drift out and back at 0.5 m/s. That drift is the V.
    - **Shared rules:**
      - pools are ring buffers of `tier.splashDrops` and `tier.splashRings`;
      - nothing is allocated after construction;
      - `castShadow = receiveShadow = false`;
      - `mesh.visible = count > 0`, so `drawCount` is 0, 1 or 2.
  - `NO_SPLASH`, returned when the area has no `waters` (the den, the neighbourhood). Every method is a no-op and `drawCount` is 0.
