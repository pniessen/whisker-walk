# Log in to My Cat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A kid brings "my cat" to any device with a cat code or a hop code. The cat's friends, colony and clan come with it. Linked devices catch up by themselves with a safe merge. A leaked code can be changed. Nobody gives an email, a password or a name.

**Architecture:** The cat key (id + secret) travels in the cloud row, so no server table about players changes. A pure three-way merge (`src/catmerge.js`) joins local, cloud and last-synced base field by field. All feature code is a lazy chunk. The database work is one hand-run file, `docs/supabase-v11-cat-login.sql`, in separate steps; the client works before and after it by feature detection (`isMissingRpc`).

**Tech Stack:** vanilla JS, vite, vitest (fake-DOM style as in `test/touchui-controls.test.js`, fake-cloud style as in `test/cloudsync.test.js`). SQL is written as files and tested by reading them (`test/v10limits.test.js` style). No live database is ever contacted by a task or a test.

**Spec:** `docs/superpowers/specs/2026-11-22-cat-login-design.md`

## Global Constraints

- Work in worktree `.worktrees/cat-login` (branch `cat-login`); commit there only. **Do not merge or push.** Each milestone is a separate branch cut from `cat-login` after the previous one is merged by the owner (`cat-login-m1`, ...), or commits on `cat-login` in order if the owner prefers one branch.
- **Do not touch the live database or Supabase** in any way (no `execute_sql`, no `apply_migration`, no connector). SQL is a file in `docs/` that the owner runs by hand or approves step by step.
- **Models:** Sonnet builds, Haiku does look-ups and runs checks. No Opus. Final review is a Sonnet read of the diff against the spec's "Review Focus" list below.
- Start-up chunk ceiling 720 kB gz (705.2 kB now). **Net change of the start-up chunk must be 0 or less; hard limit +2.0 kB.** All feature code loads with `import()`. After each milestone: `npm run build` then the buildsize test.
- Offline-first stays: no request from a device that has not linked or saved a name. `test/offlinefirst.test.js` is extended in every milestone that adds a call.
- Never print or log a code, a secret, an id or a name. Notes (`note('cloud', ...)`) carry answers only, as `onlinedelete.js` does.
- The word "family code" is not used (series switch owns it). The feature is "cat code" and "hop code".
- Everything that comes from the cloud is untrusted: it passes `sanitizeState` / `loadState` and `isPlayerId`.
- Run the full `npx vitest run` alone (parallel agents overload this Mac and heavy geometry tests time out; rerun a failure alone before believing it).
- Commit messages end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.

## Review Focus

- **Never lose:** after any merge, the set of owned items, the cats made, `lifetimePoints`, `bestWalk`, `redeemed` are each a superset of both inputs (counts at least the larger).
- **Atomic key swap:** `whisker-walk-player`, `whisker-walk-secret`, the cloud link and the save change together or not at all; a failure half-way restores the old set. Undo restores all four.
- **A walk is never interrupted** by a catch-up. The visible save changes only on the home screen.
- **No request before opt-in**, including the new boot check (a linked device only).
- **Start-up chunk** does not grow by more than 2.0 kB; the word list is lazy.
- **Old builds:** a save written by an older build (no `payload.cat`, no `social`, no `rev`) loads and syncs exactly as today.
- **Both word sets:** every new string has a phrase id and renders under both sets; no series word appears in the public bundle's code list.

## Rollout order and who does what

1. M1 (client only). Owner hand check on the Mac and iPad. Merge by owner.
2. M2 client. Merge. **Then** the owner runs v11 step 1 once both iPads have the build.
3. M3 client, then v11 step 2.
4. M4 client, then v11 step 3.
5. M5, M6.

SQL runs only after the owner says yes to that step. Between a client merge and its SQL step, the client uses its fallbacks; a test covers each fallback.

## Not in this plan

- QR scanning or any camera use.
- A "Who's playing?" list of several cats on one device (open question 3).
- Sign in with Apple, email, or any account.
- Turning on the 12-month clean-up (open question 6).
- A link form of the hop code (`#hop=...`).
- Android (owner's parked idea).
