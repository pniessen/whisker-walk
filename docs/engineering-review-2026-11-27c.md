## Findings (ranked)

### HIGH

- **P1 HIGH M: the draw-call budget for the six newest areas leaves out the walk's life.** The rows for Moon, Reef, Crystal, Treehouse, Snowville and Jungle count `build(scene)` only (`test/budget.test.js:552-587`, rows `'treehouse', 6, 2, 50200`, `'jungle', 9, 4, 36500`, `'snowville', 6, 3, 31300`). Each row's comment says the sky, flakes, fireflies, rain, rainbow, strings of lights, glows, critters and Mossy-style NPCs "are the walk's life, not in this count". The Lighthouse is the only place where the life was counted (58 meshes, about 19,000 triangles, `budget.test.js:~540`, `test/lighthousebeam.test.js`). A quick look at the life files shows new Mesh/Points/Instanced creations: `junglelife.js` 6, `snowvillelife.js` 11, `treehouselife.js` 5, `treehousewinglive.js` 1, `crystallife.js` 9, plus critter kits *(estimate: 15-40 extra draws per area, none under any ceiling)*. Treehouse T8 added 12,000 triangles and Jungle J8 7,100 in one round each, so the build rows are filling while the real frame is unmeasured. The iPad 7th gen rung is exactly where this bites.
- **P2 HIGH M: the grown River is the heaviest frame in the game, and the pins stop it getting lighter.** `test/riversouth.test.js:492` sets the worst spot at 222 meshes, 155 casters, 70,000 triangles. Casters draw twice (shadow pass), so about 377 draws plus the shadow pass at the worst spot *(estimate; the ratio is from `src/render/rig.js:196`)*. Pines 152 / 80 (`growpines.test.js:827`), Moor 119 / 55 (`moornorth.test.js:671`). Every one of those tests also asserts a LOWER bound (`worst.meshes > CEILING.meshes * 0.92`, `riversouth.test.js:506-508`; `moornorth.test.js:686-688`), so a builder who makes the strip cheaper gets a red test and has to re-pin. Strips are on by default now, so these are what a child sees, not a preview. The tests walk a grid at 5 m (`growbudget.js worstSpot`), which is fine; the problem is the ceiling's level and the ratchet in both directions.
- **O1 HIGH M: co-walk has no version handshake; an older-build partner fails silently.** Every message is `v: 1` (`src/net.js:200,220`; `netevents.js:49,152,201`; `rooms.js:240`) and nothing carries a build id or feature set. Cases I read: (a) `decideLobbyEvent` drops a `walk-config` whose area the receiver's build does not know (`src/game/lobby.js:61`), so a child on a cached older build taps "Start" with a friend in the Jungle and nothing happens, with no line saying why; (b) `area-life` events carry an arbitrary `ev` object into each area's `credit` (`netevents.js:358`); I did not read all ten `credit` validators, so treat shape checks as unknown; (c) the service worker keeps three builds (`public/sw.js KEEP_BUILDS`) and serves the cached shell offline, and the site deploys about every 10 minutes today, so mixed builds in a room are normal, not rare; (d) grow strips are now default-on while `?grow=0` still exists, so one cat can be standing where the other's ground does not exist (position messages only check `Number.isFinite`, `net.js:207-210`). Fix is small: a `build` stamp and a `proto` integer in presence, a kind line ("Sam's game is older, reload to walk together") and a toast for an unknown area.

### MED

- **L1 MED S: the service worker's page load has no timeout.** Navigations are network-first with only a `.catch` fallback (`public/sw.js` fetch handler, `isNavigation` branch). On bad wifi (a car, a hotel) the fetch hangs until the browser gives up, so a child with a fully cached game sees a white page. A 3-4 s race to the cached shell fixes it; `test/swprecache.test.js` can hold it.
- **L2 MED S: first install downloads every file of the build at once.** `precache()` does `Promise.allSettled([...files].map(cache.add))` (`public/sw.js`, in `precache`): unbounded parallel, every area, on first visit, on the same connection as start-up. Start-up alone is 666.7 kB gzipped; the areas add about 30 more files *(estimate: 2-3 MB gzipped total)*. Meanwhile `main.js:703-713` prefetches up to eight areas by hand at launch (own area, den, roofs, market, lighthouse, greenhouse, moon, reef, crystal, house when their flags are on). Both are quiet failures, so nobody sees them; on a metered phone it is data the child did not ask for. Bound the pool to 3-4 and start it after first paint is `idle`.
- **A1 MED S: nothing holds touch targets at 44 px except the chat toggle.** Only `chat-toggle` is pinned (`test/hud.test.js:592-593`). Real smaller targets in CSS: `.colony-dress select` min-height 36 (`src/style.css:1292`), `.dr-today-extras .dusk` 36 (`:1659`), `.dr-dusk-badge` 32 (`:1668`), `.dr-outfit-pic` 30 (`:1593`), `.dr-pick` 11 px text (`:1615`). 46 rules set text at 9-12 px (`grep font-size`), for example `.dr-slot small` 10 px at `:1579` and `.dr-label` 11 px at `:1556`. A 9-year-old on an iPad at arm's length is the case. A single lint test (parse the CSS for buttons, selects, summaries, `[role=button]` with a size under 44 in `touch-mode`) turns this into a list.
- **S1 MED S: the banned-word scan covers `*words.js` and per-area tests, not every text file.** `test/allwords.test.js:20` globs `src/**/*words.js` for both sets (family 'on', everyday 'off'). Ten `src/*pages.js` journal files (junglepages, treehousepages, snowvillepages, moonpages, marketpages, reefpages, crystalpages, greenhousepages, lighthousepages, roofspages), `straynames.js`, `clannames.js` and `clanphrases.js` do not match that glob. About 85 test files import `BANNED`/`bannedIn` themselves (`grep` count), so most are covered, but by opt-in: a new area whose author forgets gets no scan. `test/offwords.test.js:49` and `serieswords.source.test.js:135` already read every `src/**/*.js`, which gives a better base: scan every string literal in src (as `serieswords.source` does) in both sets, with the KNOWN_HITS list.
- **T1 MED S: the area budget file is a merge hotspot.** `test/budget.test.js` is 836 lines of which about 330 are history comments per milestone, changed 16 times in the last 300 commits; the Jungle polish merge had a conflict in it (commit 61c9ca2, "# Conflicts: test/budget.test.js"). Same pattern: `test/clanphrases.test.js` 28 changes in 300 commits, `test/lazybuild.test.js` 21, `test/fixtures/series-words-on-later.json` 17 (re-recorded again in the latest commit). Move the rows to `test/fixtures/area-budgets.json` (one line per area: meshes, casters, triangles, measured date) and the history into `docs/headroom.md`.
- **C1 MED S: CI runs only on push to `main`.** `deploy.yml:3-6` has no `pull_request` or branch trigger, so a builder's worktree is checked by `test:quick` (which skips 29 heavy files) and the first full run is the merge itself. Run 364 (int39 merge) was a failure on main (`actions/runs/45953894420`). In the last 18 runs I read: 11 cancelled by the next push, 1 failed, 6 succeeded; a good run takes 7-8 minutes wall (14:24 to 14:32, 14:08 to 14:15, 07:18 to 07:26). Cancelled runs lasted 4-7 minutes before being killed (06:36:10 to 06:40:54, 06:28:49 to 06:36:09), so most of the shard minutes billed go to commits nobody deploys. The `gate` job only looks once, at the start, so a shard already running is not stopped. A one-line check at the start of each shard step (`git ls-remote` against `$GITHUB_SHA`, `exit 0` if stale) would cut the tail; also `concurrency: cancel-in-progress: true` on group `pages` can cancel the `deploy` job itself mid-upload (GitHub's own guidance is `false` for Pages). Both estimates of minutes saved are *(estimate)*.
- **P3 MED S: the only per-frame allocation I found in the new code is small; main loop is clean.** `main.js:1270` is allocation-free by design (comment says so). New live files allocate at build, not per frame (checked `moondeeplive.js:110-125`, the C5 fix). Counts of `new THREE.*` in per-frame candidates: `player.js` 10, `crystallife.js` 32, `marketlive.js` 9, `moonroverlive.js` 6, `walk.js` 12. I did not trace which are inside `update()`; `crystallife.js` is the one to check first (largest count, most recent area). Low risk until measured.
